## Why

VitaminD today has two disconnected, insufficient authorization mechanisms: a binary `is_admin` flag in core, and a 3-tier `UserRole` enum (`OWNER`/`ADMIN`/`USER`) that only exists when `vitamind-workspace-plugin` is installed, stored as a single scalar column on the `user_workspace` pivot. A single-tenant app (no workspace plugin) has no role mechanism at all beyond admin-or-not, and even where the tier exists, it cannot represent a user holding more than one role at once, nor distinguish peer functional roles (e.g. warehouse admin vs. finance vs. sales) that don't fit a linear owner-admin-user hierarchy. Developers building domain-specific apps on the boilerplate currently have no supported way to define custom roles without building the mechanism themselves from scratch.

An initial iteration of this change was implemented directly against an earlier, less-refined version of this design (workspace ownership expressed as a `RegisterRole` tier, three workspace-plugin built-in roles). Discussion since then settled on a cleaner separation — workspace ownership as plain data, not a role, and no built-in roles at all in the workspace plugin — so this revision supersedes that implementation, which is being refactored to match.

## What Changes

- Add a new `RegisterRole` builder (in `vitamind-plugin-sdk`) for developers to statically define roles in code — the same fluent-builder-plus-static-registry pattern already used by `RegisterPage`/`RegisterPageGroup`. Registry keys are automatically prefixed by the registering package's identity, so independently chosen short keys never collide. **Implemented, matches this design.**
- Add a `user_roles` table and migration to `vitamind-core`, always present regardless of any feature flag, with generic nullable `scope_type`/`scope_id` columns (not `workspace_id`) so core stays independent of any tenancy concept while still supporting scoped role assignment. A user may hold multiple roles at once via multiple rows (many-to-many). **Implemented, matches this design.**
- Add a `RoleScopeResolver` contract to `vitamind-core` with a default `NullRoleScopeResolver` binding (always resolves to a global, unscoped role check), selectable via a `vitamin-d.role_scope_resolver` config key (a class name, defaulting to `null`) that takes priority over whichever implementation a plugin binds automatically — the same "config holds a class name, with a fallback default" pattern already used by Laravel's own `auth.providers.users.model`. **Implemented, matches this design.**
- Add `User::hasRole($role, ?scopeType = null, ?scopeId = null)` to core, falling back to the bound `RoleScopeResolver` when scope args are omitted. **Implemented, matches this design.**
- **BREAKING, supersedes an already-implemented iteration**: `vitamind-workspace-plugin` registers **no built-in roles at all**. Workspace ownership is tracked as plain data — an `owner_id` column on `workspaces`, set once at creation — entirely independent of the role-assignment mechanism. `user_workspace` is a pure membership table with no `role` column. Write access to a workspace (invite, remove, update, delete) is granted to the owner only; there is no built-in "workspace admin" tier a owner can delegate to — an app that wants that must register and check its own role. `is_admin` plays no part in workspace-level authorization, consistent with it staying fully separate from the role mechanism. This retires the previously-implemented `WorkspaceRoles` built-in tiers (`workspace.owner`/`workspace.admin`/`workspace.member`) and the tier-based `HasRolePolicies`.
- The workspace invitation flow's role selector is a single, **optional** dropdown driven by the current role registry: a fixed **Admin** option (grants `is_admin` on acceptance) plus every currently registered role (no exclusion needed — workspace-plugin registers none of its own). Choosing neither leaves the invitee a plain member with no role and no `is_admin` grant.
- `is_admin` remains a separate mechanism from the role registry — no merge, no built-in "super-admin" role, and (per the point above) no involvement in workspace-scoped authorization. The workspace invite dropdown surfaces it alongside registered roles purely as a UI convenience for the inviter.
- **Revises an already-implemented iteration**: `vitamind-core`'s `CreateUser`/`UpdateUser` actions move beyond the previously-implemented plain `admin`/`user` string toggle. The role field becomes a multi-select validated against the full `RegisterRole` registry, and selecting one or more roles performs real assignments via `user_roles`, scoped through whichever `RoleScopeResolver` is currently bound. A separate, independent `is_admin` toggle remains on the same form, orthogonal to role selection (a user can get roles, `is_admin`, both, or neither in one submission).
- Out of scope for this change: granular per-role permissions (`RegisterRole::permissions([...])`). Role checks are name-based only in this iteration.

## Capabilities

### New Capabilities
- `multi-role-authorization`: code-defined roles (`RegisterRole`), scoped many-to-many role assignment (`user_roles`), scope resolution (`RoleScopeResolver` + default binding), and the `hasRole()` check API — usable with or without any tenancy plugin installed.

### Modified Capabilities
- `vitamind-workspace-plugin`: workspace membership tiers (`OWNER`/`ADMIN`/`USER`) are removed entirely rather than re-expressed as roles. Ownership becomes plain data (`owner_id`) outside the role mechanism; there are no built-in workspace roles. Existing business constraints are preserved in this new shape (exactly one owner per workspace, owner cannot be removed, only the owner may manage the workspace or its membership).
- `vitamind-core`: `CreateUser`/`UpdateUser` gain real, multi-select role assignment via the `multi-role-authorization` mechanism, validated against the live role registry, alongside an unchanged but now-independent `is_admin` toggle.

## Impact

- **New**: `vitamind-core` migration + model changes (`user_roles` table, `RoleScopeResolver` contract, `NullRoleScopeResolver`, `User::hasRole()`, `role_scope_resolver` config key) — already implemented; `vitamind-plugin-sdk` (`RegisterRole`, with automatic package-based key prefixing) — already implemented; `owner_id` column + migration on `vitamind-workspace-plugin`'s `workspaces` table — not yet implemented.
- **Changed (refactor of an existing implementation)**: `vitamind-workspace-plugin` — remove the built-in `WorkspaceRoles` tiers and their `RegisterRole` registrations, rewrite `HasRolePolicies`/`WorkspacePolicy` against `owner_id` + membership instead of `hasRole()` tiers, update `CreateWorkspace` to set `owner_id` instead of assigning a role, make `InviteToWorkspace`'s role selection optional, update `WorkspaceUserController` owner-protection checks to use `owner_id`. `vitamind-core`'s `CreateUser`/`UpdateUser` — rework from the already-implemented plain `admin`/`user` toggle into multi-select registry-backed role assignment plus a separate `is_admin` toggle.
- **Unaffected**: `is_admin` as a mechanism (including its non-involvement in workspace authorization), `MustBeAdminMiddleware`, `UserPolicy`, `vitamind-archive-plugin` (already role-agnostic, uses ownership/visibility).
