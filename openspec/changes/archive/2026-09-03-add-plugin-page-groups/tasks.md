## 4. Migrate native entries onto the registry (backend + frontend, same cutover)

- [x] 4.1 Added `VitaminD\Core\Actions\Nav\RegisterNativeNav` (invoked from `CoreServiceProvider::boot()`'s `booted()` closure): registers Dashboard (`order: -1000`); `RegisterPageGroup` for `settings` (`order: 1000`) and `admin` (`order: 1001`, `hidden()` checks `auth()->user()->isAdmin()`).
- [x] 4.2 Registered Profile, API Keys via `group('settings')`; Users, Plugins via `group('admin')` — same titles/icons/hrefs as before.
- [x] 4.3 Registered footer entries: Horizon Dashboard, Logs (`placement('footer')`, `hidden()` checks `Route::has(...)` and `isAdmin()`); Repository, Documentation (`placement('footer')`, `external(true)`, no `hidden()`).
- [x] 4.4 Removed the hardcoded native arrays from `app-sidebar.tsx`; `mainNavItems`/`footerNavItems` now derive purely from `pluginPages` (see task 3.3). Replaced `SettingsLayout`/`AdminLayout` usage in their importers with `<SectionLayout title="Settings" groupKey="settings">` / `<SectionLayout title="Admin" groupKey="admin">` — `coreItems` is not needed since Profile/API Keys/Users/Plugins are themselves `pluginPages` entries now.
- [x] 4.5 Deleted `resources/js/layouts/settings/layout.tsx` and `resources/js/layouts/admin/layout.tsx`; updated all importers (`profile/index.tsx`, `api-keys/index.tsx`, `users/index.tsx`, `plugins/index.tsx`, `plugins/dynamic-page.tsx`, and `vitamind-workspace-plugin`'s own `resources/js/pages/index.tsx`, found via a repo-wide grep for the old import paths).
- [x] Bug found & fixed #1: `VitaminD\Core\Models\User::isAdmin()` threw a `TypeError` (declared `: bool`, returned raw `null`) for any in-memory user built via `Model::create()` without explicitly setting `is_admin` — `create()` never re-fetches the row, so the DB column's `default(false)` never reaches the in-memory attributes, and the `boolean` cast on a missing attribute yields `null`, not `false`. Nothing called `isAdmin()` before this change; `RegisterNativeNav`'s `admin` group `hidden()` closure is the first unconditional caller on every request, so it surfaced immediately as a 500 on `php artisan test`. Fixed with a defensive `(bool)` cast in `isAdmin()`.
- [x] Bug found & fixed #2: initially gated each native entry's *registration* on `Route::has(...)` (`if (Route::has('dashboard')) { ...->register(); }`), mirroring the old client-side `hasRoute()` checks. This silently dropped Dashboard/Profile/API-Keys/Users/Plugins in real app boot — `Route::has()` checked inside `CoreServiceProvider::boot()`'s `$this->app->booted()` callback does not reliably see routes other providers/route files register, even though request-time routing is unaffected (proven by manually re-invoking `RegisterNativeNav::handle()` later in the same test, where every route resolved correctly). `RegisterPage::route()` never resolves anything eagerly — it only stores a route name, resolved lazily in `toArray()`, itself never called for a hidden entry — so gating on `Route::has()` at registration time was both unnecessary and the actual bug. Fixed by always calling `register()` unconditionally and moving every `Route::has(...)` check into each entry's `hidden()` closure (evaluated per-request, after routing has definitely finished) — the same pattern already used for Horizon/Logs, now applied consistently everywhere.
- [x] Bug found & fixed #3: the `settings` group landed on the `workspaces` page instead of `Profile`, because `WorkspaceServiceProvider` registers `workspaces` directly in its own `boot()` (which always runs before any provider's `booted()` callback, including `RegisterNativeNav`'s), so "first registered" no longer reliably meant "intended primary member" once native and plugin registrations could interleave across that boundary. Fixed by changing `ResolvePluginPages`'s group-landing selection from `firstWhere('group', ...)` to `where('group', ...)->sortBy('order')->first()`, and giving `native-profile`/`native-users` an explicitly low `order` (`ORDER_PRIMARY_GROUP_MEMBER = -100`) so they always win that tiebreak.
- [x] Verified stable under `php artisan test --order-by=random` (206/206) in addition to default order, given the ordering-sensitivity of the bugs above.
